## Что еще может отказать сразу везде

В коде единых точек отказа почти не осталось; остались в том, где и как стоят
узлы. По порядку, с чего начинать:

1. **Уведомления** ([ниже](#уведомления)): сейчас о поломке узнают случайно
   (сломавшийся сервис проверки IP, медленный диск хаба). Каждый хаб и exit сам
   сообщает о FAIL своего `check`, без ноутбука.
2. **Один хостер.** Если все хабы, exit'ы и DNS управления у одного хостера,
   его авария, блокировка аккаунта или неоплата выключают все сразу. Хотя бы один
   хаб и один exit — у другого хостера (и в другой сети: два exit'а в одной /24
   друг друга не резервируют); второй домен управления — у другого
   DNS-провайдера ([ниже](#домены-управления-у-разных-dns-провайдеров)).
   Решение не в коде; в коде — ничего не мешает.
3. **Один домен на все хабы.** Хабы под одним доменом (`hub1.example.ru`,
   `hub2.example.ru`): блокировка домена или проблема его зоны — приложения не
   найдут ни один хаб, в VLESS-ссылках имя, а не IP. Хабы — под разными доменами
   (не доменом управления), плюс [`VLESS_ADDRESS`](#vless-без-dns-vless_address)
   как запасной вариант.
4. **Бэкап control.** На ноутбуке — единственная копия ключа подписи, ключа
   приказов, пароля DNS и схемы. Без него хабы работают, но восстановление —
   `hub control export` → `import` и новые токены всем хабам и exit'ам. Нужен
   `./vpn.sh control backup`: зашифрованный (age, пароль или внешний ключ) архив
   `~/vpn-control` куда-то вне ноутбука, по таймеру или напоминанием в `control check`.
5. **Exit упал — у людей на его маршруте нет интернета, кроме RU.** Это
   сознательно (IP не меняется тайком), но многим важна страна, а не IP.
   Маршрут-группа по выбору: например `cz/*` — urltest между живыми IP разных
   exit'ов одной страны; только тем, кому смена IP допустима. Имеет смысл, когда
   exit'ы этой страны в разных сетях (п. 2).
6. **Слабый хаб.** Хаб на 1 ГБ рядом с чужим сайтом: swap занят, docker однажды
   оборвал проверку конфига. Больше памяти или без соседей; `check` мог бы
   предупреждать о нехватке памяти / swap / IO (как `/proc/pressure`).
7. **Код — только с GitHub.** `update repo` и приказы control берут код из
   `REPO_URL`; если GitHub недоступен с хабов, обновления встанут (сами хабы
   работают). Зеркало: второй `REPO_URL` или получение через exit, как списки RU.

## hub2hub (обсудить)

Маршрут через соседний хаб: хаб B отдает A ключ на свой маршрут (например,
`local` B — выход с его IP в РФ), пользователей A B не знает; импортированные
маршруты дальше не отдаются, чтобы не было петель. Вопросы: зачем именно
(выход с российского IP другого региона? запасной путь до exit'а?), как такой
маршрут называется в схеме (`hub2/local`), как его проверяет `check`.

Автотесты и проверки с ноутбука есть, но руками в приложениях:

- выбор выхода — несколько профилей «SUB_NAME · маршрут» из страницы импорта

## Отдельные подписки под клиенты (косметика)

Сейчас все клиенты получают одну подписку `/<token>/sub` с заголовками
`profile-title: base64:…` и `profile-update-interval: 12`. Hiddify и NekoBox
показывают ее нормально, V2Box — нет: имя подписки «import sub (N)» и лимит 50 GB.

Пробовали (599542b, откачено) отдавать всем:

```
Content-Disposition: attachment; filename="SVOi"
profile-title: SVOi                     # без base64 для ASCII-имен
subscription-userinfo: upload=0; download=0; total=0; expire=0
```

Что вышло:

| Клиент   | Результат                                                                |
| -------- | ------------------------------------------------------------------------ |
| V2Box    | объем — бесконечность, срок — бессрочно; имя все равно «import sub (N)»   |
| NekoBox  | «истекает 1970.01.01» — `expire=0` понимает буквально                     |
| Hiddify  | лимит 857.03 GiB вместо «без лимита» на `total=0`                         |

Идея: отдельные адреса с заголовками под конкретный клиент, например
`/<token>/sub/v2box` с `subscription-userinfo` (и тем, что V2Box берет как имя),
а `/<token>/sub` оставить как есть. Кнопка V2Box на странице импорта ведет на
свой адрес.

Что выяснить:

- откуда V2Box берет имя подписки: параметр `name` в `v2box://install-sub` он,
  похоже, игнорирует, `profile-title` (plain и base64) и `Content-Disposition` — тоже;
  проверить `#name` в URL подписки, заголовок `profile-web-page-url`, имя в
  первой строке подписки;
- как V2Box показывает квоту без `expire` и с очень большим `total`
  (вдруг хватит одного адреса для всех без `expire=0`);
- откуда у Hiddify 857.03 GiB при `total=0`.

## VLESS без DNS: `VLESS_ADDRESS`

Ни домен, ни сертификат VLESS не нужны, но в `vless://` адресом стоит `DOMAIN`,
поэтому пока нет A-записи (или пока она не разошлась по резолверам) VLESS
не подключить. Настройка `VLESS_ADDRESS` в `.env` — адрес в VLESS-ссылке,
по умолчанию `DOMAIN`; можно поставить IP сервера. `./vpn.sh hub user links NAME`
печатает такую ссылку для ручного импорта. Подписка и hysteria без DNS
все равно не работают (им нужен сертификат на `DOMAIN`). Минус IP навсегда:
при переезде ссылки не следуют за A-записью, только через обновление подписки.

## Уведомления

`check` пишет только в журнал / `systemctl --failed`. Нужно сообщение в
Telegram при FAIL (токен бота и chat id в `.env`): с каждого хаба и exit'а — их
`check` и так раз в час, ноутбук для этого не нужен. Токен и chat id могут
приходить с control (хабам — в снимке, exit'ам — в записи приказов), чтобы не
настраивать каждый узел. Сообщать о смене состояния (стало FAIL / снова ok), а не
каждый час. С ноутбука `control check` по таймеру видит всю систему сразу, но
ноутбук не всегда включен — это дополнение, не замена.

## Домены управления у разных DNS-провайдеров

Сейчас все домены `CONTROL_DOMAIN` должны быть в одном аккаунте DNSmanager
(`DNS_API`, `DNS_USER`, `DNS_PASSWORD`). Резерв надежнее у другого
регистратора и DNS-хостинга: доступ к панели на каждый домен (или другой API,
например Cloudflare), публикация во все, хабам ничего менять не нужно.

## Тесты: структурировать и проработать

Логику проверять тяжело, и это уже мешает: ошибки находятся случайно или вручную.

- **Нет структуры.** `tests/templates.sh` смешивает сравнение рендера между версиями jq, поведение правил, CLI, клиента и снимки: один большой сценарий, шаги зависят от предыдущих. Нужны отдельные наборы (рендер, маршрутизация, CLI по ролям, обновления и откаты) с общими fixtures и возможностью запустить один тест.
- **Нет общей обвязки.** Загрузка функций `vpn.sh` (`eval` по диапазону строк плюс `source`) скопирована в несколько мест. Нужен один helper и один формат проверок: что ожидалось и что получилось.
- **Падения бывают молчаливыми.** При `set -e` и `pipefail` тест обрывается без сообщения (`grep` без совпадений, `local a=$1 b=$a`), а `... | grep -q` ложно падает от SIGPIPE. Нужен запуск, который всегда называет упавший шаг.
- **Тесты зависят от окружения.** `NO_PROXY` с `127.0.0.1` пускал `curl` мимо прокси, и проверка проходила вхолостую; прокси ноутбука на `127.0.0.1:2080` мог получить тестовый трафик. Тесты должны запускаться в чистом окружении, на свободных портах и без `--network host`, где это возможно.
- **Вхолостую проходящие проверки.** Намеренные поломки приходится делать вручную, и сам такой прогон легко сделать неверно: правка может просто не примениться. Нужен штатный набор мутаций, который проверяет, что правка применилась и тест упал нужной проверкой. Статические проверки не должны заслонять проверки поведения.
- **Что не покрыто вообще:**
  - настоящая цепочка клиент → хаб → exit (VLESS REALITY, Hysteria 2);
  - `+ru` и `client protocol` на настоящем соединении;
  - публикация и чтение через DNS (`dns_publish`, `cmd_sync`);
  - настоящий `cmd_update_repo` в связке с `update_run`: там стоит заглушка `vpn.sh`;
  - таблицы `control hub|exit update` и `check_exit_reports`: проверены глазами;
  - `control check` целиком.

  Нужен локальный стенд в контейнерах: хаб, exit и клиент в своей сети и подставной DNS.
- **Прочее:** `shellcheck` в тестах не запускается, общего запуска всех наборов и CI нет, полный прогон занимает минуты.
